# SVY-21326 — MCP server

Where the case stands, 2026-08-27.

---

## What was asked

> A plugin, like RestWS, that quickly creates a client from a pool and runs a function
> in it. Those functions are scope functions annotated `@Tool`. At startup it knows
> which solution is the MCP solution and scans it for tool definitions, exposing them
> at `/mcp`. Authentication is needed, so tool definitions carry an extra `userToken`
> parameter that the AI fills with the token of the user the agent acts on behalf of,
> so we can auto-login through Servoy Cloud and set the tenant.

## What was decided

Six decisions changed the shape of the case. All but the last came out of the standup
on 2026-08-25.

**It lives in core, not in a plugin.** Reaching a solution's own logic needs the
application server itself, so it runs in the application server's own process and starts and
stops with it, roughly like a batch processor. It sits in a bundle of its own, `servoy_mcp`,
which `j2db_server` uses - see below for why it is not simply part of `j2db_server`.

**A solution declares itself by its type.** A new solution type, `MCP Service`, marks
a solution as reachable over MCP. There is no configuration at all: the solution is
named in the URL, `/servoy-service/mcp/<solution>`, and one server hosts as many as it
likes. `rest_ws` works the same way.

**Tool parameters are `String`, `Number` or `JSON`. Nothing else.** A tool declaring
anything else is not published, and the log says why.

**No limits are imposed by us.** The client pool is unlimited. How many concurrent
calls a deployment runs, and what that costs in licences, is the deployment's
business.

**The protocol is the official MCP SDK's** — the same one `servoy-developer-mcp` runs.

**We do not authenticate. The solution does.** The token is never read, decoded or
verified by the server; it is passed through untouched to the solution's authenticator
module, which answers who the bearer is, what they may do and which tenant they are in.
This came out of the standup: *"you give it to the authenticator module. That
authenticator module says, I'm logging in as this user with these permissions, and this
is the tenant... So there is no authentication code in your thing."* It is what lets a
deployment mint tokens in Servoy Cloud, or use an external identity provider, or keep a
table of API keys, without any of it being our concern.

**The token travels in the `Authorization` header**, not as a tool argument. That keeps
it out of the schemas the agent sees and out of whatever the agent logs.

## What is implemented

Thirteen classes in `com.servoy.mcp`, in a bundle of their own, plus a solution type and one
line of registration. 100 tests, all passing: 77 unit and 23 integration.

**Discovery.** Every scope of the solution is walked, and any function whose
documentation block carries `@Tool` becomes a tool. The description and the parameters
come out of the JSDoc. Reaching the solution model from the server goes through
`ClientPluginAccessProvider → IApplication → FlattenedSolution`, which is the route
`FunctionDefinition.exists()` uses.

**Schema.** `@param` tags become a JSON Schema. Optional parameters, written
`@param {String} [name]`, are left out of `required`. An unsupported type takes the
whole tool out of the list, with an error in the log.

**Protocol.** The SDK's stateless HTTP transport plus a sync server, one per solution,
built on first request. Tools are registered at build time from the scan.

**Execution.** A client is borrowed from a pool keyed on solution, user and tenants -
so a client can never be handed to a different user - the identity is applied to the
session, the scope function runs, the client goes back.

**Authentication.** The bearer is handed to the solution's authenticator module through
`IApplicationServer.login` with **no client id**. That detail is load-bearing: on that
path, and only on that path, the server runs the authenticator in a throw-away client
and returns the tenant alongside the user (`getRawTenantValue()`, added by SVY-21382).
Passing a client id would apply the identity to that client and return nothing - no use
here, because the tenant has to be known *before* a client is borrowed, being part of
the pool key. The identity is then applied with `setUserUid`, `setUserName`,
`setUserGroups` and `setTenantValue`, mirroring `NGClientWebsocketSession.setUserId()`.

**Staying current.** A solution is scanned once and its tools registered when its server is
built, so something has to say when that stopped being true. Two things do. An import - the
way a solution changes under a running server - calls `McpRuntime.invalidateAll()` where it
already flushes the repository. In the developer, an `IPersistChangeListener` in
`com.servoy.eclipse.core` does the same whenever a script method is saved.

Dropping our own cache turned out not to be enough. The scan reads the solution model
through a client, and the repository hands every new client the same loaded solution until
that copy is flushed - so even a brand new client saw the old version. Invalidating now
flushes the solution's root object, and its modules' too, since a module is cached
separately but edited like any other part of the solution. Named root objects rather than
`flushAllCachedData()`: this runs on every save in the developer, and emptying the whole
repository each time would be felt across the IDE.

### What is covered

The tests are the record of what works; the table below is what they assert.

| | |
|---|---|
| `tools/list` | the marked functions, and no unsupported-type tool |
| no token | refused |
| unknown token | refused, with the authenticator's own message |
| two users | `alice`/`alice-uid` and `bob`/`bob-uid`, from two tokens |
| **tenant isolation** | same tool, no where clause: alice sees 3 acme rows, bob sees 2 globex |
| pooled client reuse | asking twice as the same user gives the same answer, never the other's |
| parameters | `add(2,40)` → 42; a JSON argument arrives as an object; an optional one may be left out |
| whole numbers | `42`, not `42.0` |
| failure paths | unknown tool, unsupported method, a path naming no solution, a notification |
| **a tool added while running** | a `@Tool` saved in a scope appears in `tools/list` and answers a call, with no restart |
| over HTTP | the endpoint is served, and the `Accept` header the SDK insists on is required |

It was also exercised by hand, before the tests existed, against a solution of the same shape
in the developer's own workspace.

Two things the testing itself taught, neither of them a fault in this code:

1. `security.login()` refuses any permission that does not exist as a group in the
   resources project, and says only "could not log in". The demo permission had to be
   created before either user could authenticate.
2. A tenant filter applies to queries **Servoy builds**. `getDataSetByQuery` with a SQL
   string goes straight to the database and comes back unfiltered, tenant column or not.
   `listMyItems` uses `QBSelect` for that reason and comes back filtered; `countRows` uses a
   SQL string and does not. Both are asserted, because the difference is not obvious.

### Five things only running found

1. The SDK resolves its **JSON mapper** and **schema validator** through
   `ServiceLoader`, from `mcp-json-jackson2` - which is not an OSGi bundle. Both are
   supplied explicitly instead, so nothing has to be embedded.
2. **Capabilities are settled at `build()`**, so tools added afterwards leave the
   server advertising none.
3. The **streamable transport needs `startAsync`**, which Servoy's filter chain does
   not support. The stateless transport does not, and fits better anyway - the state
   lives in the pool.
4. `executeMethod` resolves its context as a **form** name first; a scope needs the
   `scopes.` prefix.
5. SDK 2.0.1 refuses any request that does not send
   `Accept: application/json, text/event-stream`, which 1.1.2 accepted. Real MCP
   clients send it; curl has to be told to.

## What remains

**Error markers in Developer** for a tool with an unsupported parameter type. Johan
does not mind if they are missing; dropping the tool with a logged error is what
matters, and that is done.

**Not known:** how a user obtains their token outside a browser. It will be defined in
the cloud and does not exist yet - and it no longer blocks anything here, because the
server does not care what a token looks like. The test authenticator keeps two in a map.

**Still only two users at a time.** The pool is keyed on solution, user and tenants, and
two users have now been shown to get their own client and their own tenant. Nothing has
been run concurrently.

## The tests

`server/servoy_mcp_tests` is a fragment of `servoy_mcp`, packaged `eclipse-test-plugin`, on the
model of `com.servoy.eclipse.model.tests`. Being a fragment is what lets a test reach the
package-private parts - `extractParameters`, `toJsonType`, `quote` - without widening the API
just to be testable.

77 tests over the four classes that hold logic rather than plumbing: `McpJsDoc` (what makes a
function a tool, and what the agent is told about it), `McpToolSchema` (the JSON Schema, and the
refusal of anything that is not String, Number or JSON), `McpResults` (how a return value is
rendered, including the `Double` every number arrives as), and `McpClientKey` (the key that keeps
one user's client away from another's).

They need no server and no OSGi, so they run as an ordinary JUnit test as well as under Tycho.

`testresources/workspace/mcp_sample` is the solution the server is exercised against by hand,
kept with the tests along with its authenticator module `mcp_sample_auth`. The parsing tests read
its scope files directly, so they run against genuine documentation blocks rather than strings
written to suit the parser: if the sample changes, the tests change with it, which is the point -
the sample is what a tool is supposed to look like.

`servoy-eclipse/com.servoy.eclipse.mcp.tests` covers what needs a running developer: the pool, the
authenticator, the tenant filter, and the rescan after a scope function is saved. 23 tests, run
from `MCP Integration Tests_mac.launch` as a JUnit plug-in test - about 18 seconds, including
starting a developer on a scratch workspace. It lives in `servoy-eclipse` rather than next to the
unit tests because the `server` repository builds only `j2db_log4j`, `servoy_mcp` and
`j2db_server` - it cannot see `com.servoy.eclipse.core`, and driving the IDE needs it.

The launch configuration is derived from `RenamePersistIntegrationTest_mac.launch` in
`com.servoy.eclipse.developer.mcp.tests`, changing only the project, the test class and the
workspace. That is worth knowing: an integration launch has a curated list of some 450 bundles and
a handful of settings that were arrived at by trial, and building one from scratch is a day lost.

`McpHarnessSmokeTest` runs first and touches nothing. It exists because "no tests ran" and "every
test failed" look identical from outside, and telling them apart decides where to look.

Only one test goes over HTTP, for what a direct call cannot show: that the bundle resolved in OSGi
with the SDK on its own class path, that `registerWebService` ran, that `WebServicesServlet` routes
to us, and that the `Accept` header the SDK insists on is really required. The rest drive
`McpServlet` with a request and response made by a dynamic proxy - the same approach
`BearerTokenAuthenticationFilterTest` takes. The proxy has to offer `getInputStream()`, not just
`getReader()`: the SDK's transport reads the body as a stream.

The workspace those tests run in is `mcp_sample` again, with its authenticator module and a
resources project carrying the `mcp_user` permission and the tenant column. It is deliberately
minimal - two scopes and their metadata, no forms and no media - because a solution that references
a web package stops the developer with a modal dialog asking to install it, and a test cannot
answer a dialog. The rows the tenant test filters are created in SQL at start-up, through the
Servoy server rather than through `DriverManager`, since the database behind `example_data` is
whatever the developer is configured against.

One of those tests pins something worth knowing about writing tools: `salesTools_listMyItems` uses
`QBSelect` and comes back filtered by tenant, three rows for one user and two for the other, while
`salesTools_countRows` asks with a SQL string and comes back with all five. A tenant filter applies
to queries Servoy builds. It is the mistake someone writing a tool will make, so it has a test.

### Why its own bundle

The SDK must not become a dependency of the shared build - adding `mcp-core`,
`reactor-core` and `reactive-streams` to `com.servoy.eclipse.target.target` would make
every developer download them, for code most of them never touch. So `servoy_mcp`
carries the three jars on its own `Bundle-ClassPath` and imports nothing from the
platform, exactly as `com.servoy.eclipse.developer.mcp` carries its embedded Tomcat.
The official target is untouched.

The bundle is named `servoy_mcp`, not `j2db_*`: `j2db` is the historical root namespace
and reads like a database. The package is `com.servoy.mcp`, following `com.servoy.base`
rather than nesting under `com.servoy.j2db`.

The coupling to `j2db_server` runs one way only - it imports `com.servoy.mcp` for the
one registration call. Nothing in `servoy_mcp` refers back.

## The sample solution

`mcp_sample` is of type `MCP Service` and carries the `@Tool` functions in two scopes. It ships
with both test bundles, and the parsing tests read its scope files directly, so what the tests
run against and what a person tries by hand cannot drift apart.

`mcp_sample_auth` is its authenticator module: `globals.js` holds a map of two tokens, and
`onOpen(arg, parameters)` reads `parameters.userToken`, calls `security.login()` and
`security.setTenantValue()`. Refusing is simply not calling `security.login()` - the user uid
stays null and the server answers the agent with a refusal.

| token | user | tenant |
|---|---|---|
| `mcp-demo-token-alice` | alice | acme |
| `mcp-demo-token-bob` | bob | globex |

The tenant demonstration needs data to filter: `example_data.mcp_tenant_demo` holds three acme
rows and two globex ones, with `tenant_name` flagged as a Tenant column in its `.dbi`. The
integration tests create that table and its rows at start-up. The permission `mcp_user` has to
exist in the resources project, or `security.login()` refuses - it is in the resources project
that ships with the tests.

The solution is deliberately minimal: two scopes and their metadata, no forms and no media. A
solution that references a web package stops the developer with a modal dialog asking to install
it, and a test cannot answer a dialog.
