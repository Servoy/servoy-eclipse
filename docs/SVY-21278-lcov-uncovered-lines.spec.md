# SVY-21278: LCOV Code Coverage Should Report Uncovered Lines

| Field        | Value                                                        |
|--------------|--------------------------------------------------------------|
| Jira         | [SVY-21278](https://servoy-cloud.atlassian.net/browse/SVY-21278) |
| Priority     | Minor                                                        |
| Fix Version  | 2026.9.0                                                     |
| Related      | [SVY-20918](https://servoy-cloud.atlassian.net/browse/SVY-20918) (Code coverage reporting in unit test) |

## Goal

The LCOV files generated by `ServoyJSUnitTestRunner` must include `DA:<line>,0` records for uncovered (reachable but never executed) lines, in addition to the existing `DA:<line>,<count>` records for covered lines. Non-executable lines (comments, blank lines, declarations) must be omitted entirely from the DA list. Per-file `LF:` (lines found) and `LH:` (lines hit) summary records must also be emitted.

## Background

SVY-20918 introduced line-hit tracking to the Servoy JSUnit test runner. The existing LCOV output only emitted `DA` records for lines where the hit count was greater than zero. This made it impossible for coverage visualization tools (IDE gutters, CI dashboards) to distinguish between lines that were never reached and lines that are simply not executable. The [LCOV format specification](https://ltp.sourceforge.net/coverage/lcov/geninfo.1.php) requires:

- `DA:<line_number>,<execution_count>` for every executable line — including `DA:<line>,0` for lines that could have been executed but were not.
- Non-executable lines (comments, whitespace, declarations without side effects) are completely omitted from DA records.
- `LF:<count>` — total number of instrumented lines (lines found).
- `LH:<count>` — number of lines with at least one hit (lines hit).

The challenge is determining which lines are "executable" (reachable). Rhino provides this information through its debug interfaces — the set of lines on which breakpoints can be set — but it uses inconsistent source name conventions depending on compilation mode.

## Design

### Data Sources

The implementation cross-references two data structures obtained from `SolutionJSTestSuite`:

1. **`getLineNumbers()`** — `Map<String, Map<String, Map<String, Map<Integer, Integer>>>>` (type → scopeName → funcName → lineNumber → hitCount). Contains only lines that were actually executed. Function names use `""` (empty string) for top-level/anonymous code.

2. **`getReachableLines()`** — `Map<String, Map<String, Set<Integer>>>` (sourceName → funcName → reachableLineNumbers). Contains all lines where Rhino can set breakpoints. Function names use `"<top-level>"` for anonymous code.

### LCOV Generation Algorithm (per function)

For each function within a scope/form:

1. Resolve the reachable lines for the function via `findReachableLinesForFunction()`.
2. Build a sorted union (`TreeSet`) of all lines: hit lines from `lineNumbers` + reachable lines from `reachableLines`.
3. For each line in the union:
   - Emit `DA:<line>,<hitCount>` if the line was hit (count > 0).
   - Emit `DA:<line>,0` if the line is reachable but was never hit.
4. After all functions in a source file, emit `LF:<total_da_lines>` and `LH:<lines_with_count_gt_0>`.

### Rhino Source Name Patterns

Rhino uses two different source name conventions depending on how scripts are compiled:

#### Pattern 1: File-level source name

The source name is a filesystem path like `C:\path\to\scopeName.js` or `scopeName.js`. All functions within the file appear as inner keys in the map:

```
"globals.js" → { "<top-level>" → {1,2,5}, "myFunc" → {8,9,10} }
```

#### Pattern 2: Per-function source name

Each function is a separate top-level entry with a path like `solution/scopes/scopeName/funcName`:

```
"mySolution/scopes/globals/myFunc" → { "<top-level>" → {8,9,10} }
```

### Source Name Resolution

**`findReachableForScope(reachableLines, type, scopeName)`** resolves the file-level map by trying candidate keys in priority order:

- For scopes: `scopeName.js`, `scopes/scopeName.js`, `scopeName`
- For forms: `forms/formName.js`, `formName.js`, `forms/formName`, `formName`
- Fallback: iterate all keys looking for suffix matches (`/scopeName.js`, `\scopeName.js`)

**`findReachableLinesForFunction(reachableLines, reachableForScope, type, scopeName, funcName)`** resolves lines for a specific function:

1. Direct lookup in the scope-level map (Pattern 1). For empty/null funcName, also tries `"<top-level>"`.
2. If not found, searches for per-function source names (Pattern 2) matching `/<typeDir>/<scopeName>/<funcName>`.
3. Merges all inner map entries (usually just `"<top-level>"`) into a single set.

### Anonymous Function Name Mismatch

The `lineNumbers` map uses `""` (empty string) for top-level/anonymous code, while `reachableLines` uses `"<top-level>"`. The `findReachableLinesForFunction` helper handles this by checking for `"<top-level>"` when `funcName` is null or empty.

## Implementation Plan

All changes are in a single file:

**`j2db_test/src/com/servoy/automation/jsunit/smartclient/ServoyJSUnitTestRunner.java`**

1. In the `tearDown()` LCOV generation loop (both scopes and forms sections):
   - Call `findReachableForScope()` to resolve the reachable map for the current scope/form.
   - Track `LF`/`LH` counters in a two-element `int[]` array.
   - For each function, call `findReachableLinesForFunction()` and build a `TreeSet` union of hit lines and reachable lines.
   - Emit `DA:<line>,<count>` for every line in the union (count defaults to 0 via `getOrDefault`).
   - Increment LF for every DA line; increment LH only when count > 0.
   - After all functions, emit `LF:` and `LH:` summary records before `end_of_record`.

2. Add helper method `findReachableForScope(reachableLines, type, scopeName)`:
   - Tries multiple candidate source name keys.
   - Falls back to suffix-based iteration.

3. Add helper method `findReachableLinesForFunction(reachableLines, reachableForScope, type, scopeName, funcName)`:
   - Direct lookup with `"<top-level>"` fallback.
   - Per-function source name pattern matching.
   - Merges inner map values into a single `HashSet`.

## Acceptance Criteria

1. **Uncovered lines reported**: LCOV output includes `DA:<line>,0` for every reachable line that was not executed during the test run.
2. **Covered lines still reported**: LCOV output includes `DA:<line>,<count>` (count > 0) for every executed line.
3. **Non-executable lines omitted**: Lines that are not in either the hit set or the reachable set (comments, blank lines, non-code declarations) do not appear as DA records.
4. **LF/LH summaries present**: Each `end_of_record` section is preceded by `LF:<n>` and `LH:<m>` where n = total DA lines and m = lines with count > 0.
5. **Both source name patterns handled**: Coverage is correctly reported regardless of whether Rhino uses file-level or per-function source name compilation.
6. **Anonymous function name mismatch handled**: Top-level code (funcName = `""` in lineNumbers) correctly matches `"<top-level>"` in reachableLines.
7. **Scopes and forms both covered**: The logic applies identically to both scope-level and form-level JavaScript files.
8. **No regression**: Existing LCOV output for covered lines (SF, FN, FNF, FNH, FNDA records) is unchanged.
